0.2 先给结论：对你原设想的 6 处修正

这 6 条决定项目能不能落地，建议逐条看。

修正 1｜UltraRAG 的 MCP 是“内部总线”，不是现成的“入库 API”。
官方文档把 corpus、retriever、reranker、evaluation 等模块做成 MCP Server，由自带的 MCP Client 按 YAML 流水线串联；对外的编程入口是 ultrarag.api 的 ToolCall / PipelineCall 和 CLI。也就是说，“让 LangGraph 直接通过 MCP 调用 UltraRAG 的文档注入工具”这一步，中间需要补一个薄适配层（本草案的 rag-service，约 30–100 行）。这不是坏消息：有了这层，UltraRAG 换版本、甚至换实现，主 Agent 都不用改。

修正 2｜元数据抽取不要全交给 LLM“规划”。
作者、标题、年份、DOI、arXiv ID 用 arXiv API / Crossref 确定性抓取；LLM 只补“量子比特类型、方法、器件、材料”这类语义标签。好处：不编造 DOI、可复现、便宜、失败可重试。

修正 3｜“多模态实验数据”要拆成两类，不要混在一个库里。
论文里的脉冲序列图、能级图、参数热力图属于“文献图像”，用 VisRAG 按页图像检索，回答时把原图给你看；你自己实验产生的热力图、时间序列属于“结构化数据”，存 CSV/Parquet + 元数据，让代码现场重画。把旧图当知识检索，既不准也不可复现。

修正 4｜“每天自动吃 arXiv”必须先过质量门，否则越吃越差。
无过滤的自动入库会把知识库变成垃圾场：不相关论文、解析失败的公式、重复预印本都会稀释检索。正确链路是 staging（待审区）→ 相关性/解析质量打分 → 小评测 → 人工一键批准 → 晋升生产库 → 可回滚。自我进化 = 有评测的进化，不是无脑吞。

修正 5｜“LangChain 规划”应改为“LangGraph 编排”。
LangChain 是组件库（模型、检索器、工具），不负责有状态的多步规划；LangGraph 才是“大脑”：状态、分支、循环、人工中断、断点续跑。两者同属一个生态，不冲突。

修正 6｜入口先做 Streamlit，插件和桌面放二期。
Streamlit 一周能出可用界面；Jupyter/VS Code 插件和桌面打包各要 1–3 周，会分散你验证“科研价值”的精力。先用网页把闭环跑通，再谈入口形态。

0.3 本草案的假设

  • 单机 Windows 10/11，Python 3.11.9，已有 DeepSeek API key；无 GPU 也能跑，有 GPU 更快。
  • 中文界面，英文文献；回答以中文为主，引用保留英文原文。
  • 你每周能投入 3–4 小时 × 4–5 天；先以“能演示、能验收”为目标，不以论文级完美为目标。
  • 实验室数据默认只在本机；是否允许上云，是 §14 的第 1 个问题。

1.3 非功能需求（NFR）

  • 本地优先：默认单机运行；除 DeepSeek API 外不依赖外部服务。
  • 可复现：每次回答/分析记录模型名、参数、KB 快照、数据哈希。
  • 可维护：模块少、目录清晰、配置集中；关键文件有中文注释。
  • 性能：问答 P50 < 15 秒；代码分析任务 < 120 秒；入库单篇 3–10 分钟（CPU）。
  • 成本：有月度预算上限与超限降级策略（先检索、少调用大模型）。
  • 安全：论文文本视为不可信输入（防提示注入）；生成代码不得读密钥、不得写原始数据。
  • 语言：界面中文；术语中英对照；引用保留原文。

1.4 明确不做（v1 范围外）

  • 不连接/控制任何仪器，不写实验参数，不替代实验物理学家做安全判断。
  • 不自动把未发表数据发到云端；默认需你显式授权。
  • 不做多用户、账号、权限系统。
  • 不微调/训练模型；不做论文全文翻译（可后加）。
  • 不自动删除知识库文档（只归档/标记）。
  • 不做桌面安装包和手机端（二期再说）。

2. 总体架构

2.1 三条设计原则

  1. 规划与检索分离：主 Agent 负责“想做什么”，RAG 服务负责“知道什么”。主 Agent 不直接读写向量库，RAG 不替 Agent 做任务规划。
  2. 契约先行：两边只通过 MCP 工具契约通信（kb.search / kb.ingest / …）。UltraRAG 是“实现 A”，自建轻量 RAG 是“实现 B”，随时可换。
  3. 一切可追溯：回答 = 结论 + 证据（chunk_id/页码）+ KB 快照；分析 = 参数 + 脚本 + 数据哈希 + 环境版本。

2.3 四条主数据流

A. 问答流
UI → Agent 路由 → 查询改写（中文→英文术语、缩写展开）→ kb.search（分层 + 过滤）→ 重排 → 证据充足性判断（不足则再检索，最多 3 轮）→ 生成回答（每个结论挂引用）→ 引用校验 → 返回。

B. 实验分析流
上传 CSV → 数据画像（列、单位、缺失）→ 识别测量类型 → 选拟合模板 → 生成代码 → 沙箱执行 → 检查残差/图 → 不通过则修（≤3 次）→ 输出参数表、图、报告、科研档案记录。

C. 入库流
PDF/URL/arXiv ID → 去重 → 元数据（确定性 + LLM 补标签）→ MinerU 解析 → 质量评分 → 结构感知切块 → 嵌入 → 写入影子索引 → 冒烟检索 → 入库报告 → 你批准 → 晋升生产库 + 快照。

D. 自更新流
每日定时 → arXiv API 抓取 → 相关性过滤 → 下载到 staging → 解析/索引（影子）→ 生成摘要 → 你审批 → 晋升 → 跑回归评测 → 不达标则回滚。

2.4 选型与理由

层 选型 为什么 备选 / 风险
编排 LangGraph 有状态图、循环、人工中断、断点续跑 自写状态机（不推荐，维护成本高）
知识层 UltraRAG 科研向、MCP 模块化、MinerU/VisRAG 内置、有评测 版本较新，接口可能变；需适配层
集成 MCP（stdio） 本地进程、低延迟、工具契约清晰 REST（跨机时再用）
界面 Streamlit 一周出可用界面，图表/上传/聊天都简单 Gradio（更轻，但布局弱）
向量索引 FAISS（CPU） Windows 好装、够用；重建快 Milvus（大规模/增量，但 Windows 需 WSL/Docker）
元数据 SQLite 单文件、零运维、可备份 DuckDB（分析型，后加）
对话模型 DeepSeek deepseek-flash 已有 key，便宜，课程里验证过 本地 Qwen（隐私模式，需 GPU）
Embedding Qwen3-Embedding-0.6B 中英多语、CPU 可跑、1024 维 bge-m3（更稳，稍慢）
重排 bge-reranker-v2-m3 中文/英文都可以，CPU 可跑 先用向量分数，后加重排
PDF 解析 MinerU（UltraRAG 内置） 公式/版面好，中文生态 Marker / docling（备选）
拟合 lmfit + numpy/scipy 参数带误差、模型声明式、社区大 手写 scipy.curve_fit（不推荐）
定时 Windows 任务计划程序 重启后仍生效，零常驻进程 APScheduler（进程内，重启丢失）

2.5 部署形态

  • v1：一台 Windows 电脑，三个进程：Streamlit UI、Agent 运行时（被 UI 调起）、rag-service（由 Agent 以 stdio 启动）。UltraRAG 在 rag-service 进程内以 Python API 调用。
  • 依赖隔离：.venv-agent（LangGraph/Streamlit/lmfit）与 .venv-rag（UltraRAG/MinerU/FAISS）分开，避免依赖打架。
  • 不强制 Docker：UltraRAG 官方支持 uv 源码安装；Windows 装不上时再用官方 CPU 镜像（端口 5050）兜底。
  • Windows 注意：路径含中文/空格要加引号；项目放浅目录（如 D:\qlab）避免长路径；.bat 正文只用 ASCII，中文文件名用 start "" "..." 打开。

3.4 代码执行沙箱

  • 运行方式：subprocess 调 .venv-agent 的 Python，工作目录 runs/<run_id>/，timeout=120s，stdout/stderr 截断到 20KB。
  • 数据隔离：原始数据只读（复制或只读挂载）；输出只能写 runs/；环境变量里不放 API key。
  • 输出协议：脚本必须写 result.json（状态、指标、图路径、错误摘要）；Agent 读它做判断，不靠“猜 stdout”。
  • 硬隔离的诚实说明：Windows 上 v1 做不到真正内核级隔离；先做到“目录隔离 + 超时 + 无密钥 + 可审计”。真要强隔离，二期用 Docker/WSL 或单独低权限用户。
  • 禁止清单：改 data/raw、删文件、发网络请求、读 .env、调用仪器 SDK。发现即拒绝并记录。

4. 知识层设计（UltraRAG）

4.1 UltraRAG 能做什么、不能做什么

能做（官方文档确认） 需要你补的

关键结论：不要让 LangGraph 直接依赖 UltraRAG 的内部 YAML 或 Server 路径。中间加一层 rag-service（MCP Server），把“检索/入库/状态/统计”封装成稳定工具。UltraRAG 的 generation 模块默认关闭——回答由主 Agent 生成，才能统一引用、记忆和风格。

4.3 解析管线（单篇论文）

  1. 下载 PDF → 存 data/raw/<doc_id>.pdf，记 SHA-256。
  2. 元数据：arXiv API / Crossref 确定性抓取；LLM 补 platform/techniques/tags。
  3. MinerU 解析：输出 Markdown、图片、版面 JSON（公式保留 LaTeX）。
  4. 质量检查：文本长度、公式数量、乱码率、图片数；低于阈值进隔离区。
  5. 图表关联：图注 ↔ 图文件 ↔ 所在页；表转 Markdown。
  6. （可选）VisRAG：图表密集页转 144DPI 图像，走多模态索引。
  7. 去重：DOI/arXiv ID 精确去重 + 标题规范化 + SimHash 近重。
  8. 切块（见 §4.4）→ 嵌入 → 写影子索引。
  9. 冒烟检索：用摘要生成 3 个问题，命中率 < 2/3 则标记“待人工检查”。
  10. 生成入库报告：页数、公式数、图数、警告、耗时。

4.4 切块策略

  • 结构感知：按章节/小节切，保留 section_path（如 3.2 Readout fidelity）。
  • 大小：400–800 tokens，重叠 15%；公式/图/表单独成块，不与正文混。
  • 块类型：text / formula / figure / table / algorithm。
  • 元数据随块走：doc_id、page、figure_id、section_path、layer、year。
  • 标题前缀：每块开头拼“论文简称 + 章节”，提升短查询命中率。
  • 注意：UltraRAG 自带切块偏通用；公式/图表密集的论文，建议先用我们自己的结构感知切块器产出 JSONL，再交给 UltraRAG 的 retriever_embed/index。这是允许的，也是推荐的。

4.6 检索策略

  1. 查询改写：中文→英文术语；缩写展开（T1/T2/TLS/Purcell）；抽元数据过滤条件（年份、平台、层）。
  2. 混合检索：BM25 + 向量，RRF 融合；每路 top 30。
  3. 重排：cross-encoder 取 top 8；CPU 慢时只对 top 15 重排。
  4. 加权：L3/L5（实验室知识）> L1（综述）> L2（arXiv，按时间衰减）。
  5. 去重：同一论文相邻块合并；近重复块丢弃。
  6. 上下文预算：6–8k tokens；每条证据带 chunk_id、页码、图号。
  7. 多模态：问题涉及“图/脉冲序列/热图”时，额外走 VisRAG 图像检索，把原图返回给 UI。

4.8 去重、版本、快照、增量

  • 去重：DOI/arXiv ID 精确匹配；标题小写去标点后匹配；正文 SimHash 64 位，Hamming ≤ 3 视为近重。
  • 版本：同一论文的 v1/v2 保留一条“最新”，旧版标记 superseded，不物理删除。
  • 快照：每次批量变更生成 kb/snapshots/<date>/manifest.json + 索引副本；出问题一键回滚。
  • 增量：FAISS 后端下新增文档通常要重建索引；采用“按月分片索引 + 夜间重建”，检索时跨分片合并。文档登记表（SQLite）是唯一事实源，索引只是派生数据。

5. 自我进化（Agentic RAG）

5.1 单篇论文入库（时序）

  1. 你拖入 PDF / 粘贴 arXiv 链接 / 输入 DOI。
  2. Agent 校验文件、算哈希、查重；重复则问“更新还是跳过”。
  3. 确定性抓元数据（arXiv/Crossref），LLM 补标签。
  4. 创建异步任务（job_id），UI 显示进度。
  5. MinerU 解析 → 质量评分；失败则 OCR 兜底或隔离。
  6. 结构感知切块 → 嵌入 → 写影子索引。
  7. 冒烟检索（3 个问题）→ 生成入库报告。
  8. 你在 UI 查看报告，点“批准入库”。
  9. 晋升生产索引 + 写快照 + 登记科研档案。
  10. 失败分支：解析失败可重试；质量低进隔离区；重复可覆盖/跳过。

5.2 arXiv 每日任务

  • 时间：每天 08:00（Windows 任务计划程序调 scripts/daily_arxiv.py）。
  • 来源：arXiv API（export.arxiv.org/api/query），分类 quant-ph、cond-mat.mes-hall、physics.app-ph；关键词如 transmon、decoherence、readout、TLS、Purcell。
  • 流程：检索 → 相关性打分（与实验室 profile 的 embedding 相似度）→ 下载 PDF 到 data/staging/ → 解析/影子索引 → 生成摘要 → 待审队列。
  • 限额：每天最多 20 篇；请求间隔 ≥ 3 秒；失败重试 2 次；连续失败则暂停并通知。
  • 摘要格式：标题、作者、3 行摘要、相关性分、为什么可能相关、原文链接、批准/拒绝按钮。
  • 合规：遵守 arXiv 使用条款；只下载元数据+PDF 供个人研究；不重新分发全文。

5.3 质量门（晋升生产库的条件）

检查 阈值 不通过的处理
相关性（与实验室主题） ≥ 0.65 留在 staging / 丢弃
解析质量 ≥ 0.70 隔离，人工抽查
去重 无近重 提示合并/跳过
冒烟检索 3 题中 ≥ 2 标记待查
回归评测 不掉点 > 3% 阻止晋升
人工批准 前 4 周必须 未批准不进生产库

5.4 评测闭环（自我进化的刹车）

  • 黄金集：40 道问答（检索+回答）、15 个分析任务（拟合/诊断）。
  • 指标：recall@10、引用准确率、忠实度（LLM 评判 + 10% 人工抽查）、回答正确率、代码成功率、参数回收误差、诊断 top-3 命中率。
  • 门槛：recall@10 ≥ 0.85；引用准确率 ≥ 0.90；忠实度 ≥ 0.90；拟合误差 < 5%；诊断 top-3 ≥ 0.70。
  • 执行：每次 KB 快照晋升前自动跑；结果存 eval/results/<snapshot>.json；掉点 > 3% 阻止晋升。

5.5 知识缺口驱动采集

  • 记录“低置信问题”：无 chunk 超过阈值、校验失败、你点“没回答好”。
  • 每周生成缺口报告：Top 20 问题 → 建议检索词/候选论文。
  • Agent 提议，你批准后抓取；不自动扩张。

5.6 成本控制

  • 每次调用记 tokens_in/tokens_out/耗时/估算费用 到 costs 表。
  • 月度预算上限写进配置；超限后降级：只检索不生成、或换更小模型。
  • 缓存：同一问题 + 同一 KB 快照 + 同一模型，命中缓存直接返回。
  • 先跑 100 次真实使用，再谈定价；不要拍脑袋估算。

6. 实验数据分析子系统

6.1 数据接入

  • CSV 约定：长表优先（run_id, sweep_param, x, y, ...）；表头带单位（如 time_us、amp_mV）；同名 sidecar *.meta.yaml 存实验参数。

6.3 拟合与不确定度

  • 用 lmfit：声明模型、给初值与边界；初值从峰值/FFT/分位数启发式给出。

  • 可辨识性检查：参数相关性 > 0.95 时提示“这组数据定不住这个参数”。
  • 合成数据回归：每个模板必须有“生成→加噪→拟合→回收”的测试，误差门槛 < 5%。

6.6 证据等级

  • A：文献直接实验/理论 + 你的数据支持。
